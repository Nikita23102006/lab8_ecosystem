## Описание решений

### Средней сложности №4 — TDD для калькулятора

Работа велась по циклу TDD, и он виден в истории коммитов:

1. **красный** — коммит `test: add failing calculator tests (TDD red)`:
   тесты без реализации, `pytest` падает — модуля ещё нет;
2. **зелёный** — `feat: minimal calculator passing all tests (TDD green, task 4)`:
   простейший код, проходящий все тесты;
3. **рефакторинг** — `refactor: use operator tables and bounded history (TDD refactor)`:
   таблицы операций вместо цепочек `if`, `deque` для истории, общие проверки;
   тесты не менялись и остались зелёными.

Любой этап можно проверить: `git checkout <хеш коммита> && python3 -m pytest
tests/test_task04_calculator.py`, затем `git checkout main`.

Калькулятор умеет базовые операции, степень, корень, проценты и вычисление
выражений из строки (`"2 + 3 ^ 2"`, `"sqrt(16) + 1"`, `"(2 + 3) * 4"`).

Выражения разбираются модулем `ast` с обходом дерева по белому списку
операций — **без `eval()`**. Тесты проверяют, что `__import__('os')`,
`open(...)`, имена переменных и прочее отклоняются. Защита от «бомб»:
ограничены длина выражения и степень (`9^9^9` не повесит программу),
переполнение и комплексный результат дают понятную ошибку.

54 теста, многие параметризованы через `pytest.mark.parametrize`.

### Средней сложности №8 — CLI на argparse

- подкоманды `add`, `sub`, `mul`, `div`, `pow`, `sqrt`, `percent`, `eval`, `ask`;
- собственный тип аргумента `number` — принимает и `2.5`, и `2,5`;
- общие флаги `--json`, `--precision`, `--verbose` работают и до команды,
  и после неё (`argparse.SUPPRESS` в подкомандах);
- `--version`, автоматическая справка `--help` по каждой команде;
- коды выхода: 0 — успех, 1 — ошибка вычисления (в stderr), 2 — неверные
  аргументы;
- `main(argv)` принимает список аргументов, поэтому CLI тестируется без
  запуска процесса; один тест всё же запускает настоящий процесс.

### Средней сложности №10 — архитектура MVC

Описание — в `task10_mvc_architecture.md`, с диаграммами Mermaid
(GitHub показывает их как картинки):

- **Model** — `task04_calculator.py`, `adv08_ai_client.py`;
- **View** — `views.py` (текст и JSON), Pydantic-схемы ответов сервиса;
- **Controller** — `task08_cli.py` и `adv01_service.py`.

Одна модель обслуживает два интерфейса. Правила зависимостей между слоями
проверяет тест `tests/test_architecture.py`: он разбирает импорты модулей
через `ast` и падает, если модель импортирует контроллер или представление.

### Повышенной сложности №1 — микросервис на FastAPI

| Метод | Адрес | Что делает | Ошибки |
|---|---|---|---|
| GET | `/health` | проверка живости | — |
| POST | `/calculate` | вычислить выражение | 400 — ошибка вычисления, 422 — неверное тело |
| GET | `/history` | история вычислений | — |
| DELETE | `/history` | очистить историю | — |
| POST | `/ask` | вопрос к ИИ | 502 — ошибка ИИ, 503 — ИИ не настроен |

Калькулятор и ИИ-ассистент передаются в обработчики через `Depends`,
поэтому в тестах они подменяются через `app.dependency_overrides`.

### Повышенной сложности №8 — интеграция внешнего ИИ API

ИИ переводит вопрос на русском языке в выражение, а считает его калькулятор.
Ответ модели **никогда не выполняется как код**: он проверяется по белому
списку символов и вычисляется безопасным разбором из задания №4. Тест
проверяет, что «ответ» с `__import__('pathlib').Path(...).touch()`
не создаёт файл.

Поставщики:

- **Anthropic Messages API** (Claude) — `AnthropicProvider`;
- **любой OpenAI-совместимый API** — OpenAI, многие другие сервисы,
  локальный Ollama — `OpenAICompatibleProvider`;
- **offline** — правила без сети; используется по умолчанию, чтобы программа
  работала у проверяющего без ключей.

Настройка — переменными окружения:

```bash
export AI_PROVIDER=anthropic          # или openai, или offline
export AI_API_KEY=ваш_ключ
export AI_MODEL=название_модели
export AI_BASE_URL=http://localhost:11434/v1   # только для openai-совместимых
python3 task08_cli.py ask "сколько будет 15 процентов от 2400"
```

Сетевые ошибки, таймаут, HTTP-ошибки и неожиданный формат ответа переводятся
в понятное `AIError`. Запросы к API проверяются тестами через
`httpx.MockTransport` — без реальной сети и ключей: тест смотрит адрес,
заголовки (`x-api-key`, `anthropic-version`, `Authorization`) и тело запроса.
